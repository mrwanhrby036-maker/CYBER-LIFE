# الأمان

## المصادقة والتفويض

- الإنتاج: Firebase ID token يُحقق منه الخادم عبر Admin SDK (`verify_id_token`)، ثم يُقرأ الدور من `admin_roles/{uid}` أو قائمة `CYBERLIFE_ADMIN_UIDS`.
- التطوير: جلسات محلية موقعة بـ HMAC، كلمات مرور scrypt. **مرفوضة في الإنتاج**.
- كل مسار طالب يتطلب مستخدمًا نشطًا؛ مسارات `/api/admin/*` تتطلب دور admin.
- حماية IDOR: كل قراءة/كتابة تقدم/تقارير/مهام مقيدة بـ `uid` الجلسة؛ الأدمن فقط يرى الجميع.

## قاعدة البيانات

- كل الكتابات من الخادم فقط؛ قواعد RTDB `.write:false` على كل العقد.
- `assessment_keys` و `team_names` غير مقروءة للعميل.
- `curriculum/missions` و `curriculum/laboratory` غير مقروءة مباشرة لأنها تحتوي مفاتيح؛ الخادم يرسل نسخة منزوعة المفاتيح.
- القواعد تسمح فقط بالقراءة للمالك/العضو/الأدمن حسب العقدة.

## الأسرار

- لا توجد مفاتيح في Git. `.env` و service-account مستثناة في `.gitignore`.
- الواجهة تستخدم فقط Firebase Web App config العام؛ لا Admin SDK في المتصفح.
- الخادم يقرأ service-account من ملف أو JSON بيئي.

## مدخلات ومخرجات

- Pydantic يتحقق من الأجسام؛ حدود طول صارمة.
- `escapeHtml` في الواجهة لكل نص ديناميكي؛ لا `innerHTML` غير معقم لمحتوى المستخدم.
- المختبر لا يستخدم `eval`/`exec`/`subprocess`؛ قائمة أوامر مسموحة وملفات اصطناعية.
- أخطاء آمنة: رسائل عربية عامة + `request_id`، بدون stack traces للعميل.

## الشبكة

- CORS بقائمة أصول صريحة؛ الإنتاج يرفض `*` ويشترط HTTPS.
- Rate limiting لكل عملية (per-process). **قيد معروف**: عند تعدد النسخ يجب استخدام limiter مشترك (Redis مثلًا) قبل الإنتاج العام.
- حدود حجم الجسم، رؤوس أمان، سجل تدقيق للعمليات الإدارية.

## ما لم يُختبر بعد

- قواعد RTDB لم تُختبر على Firebase Emulator في هذه البيئة (لا توجد اعتمادات). الاختبارات الحالية تتحقق من بنية القواعد ومنع الكتابة العامة.
- تدفق Google Sign-In الحقيقي يحتاج إعداد Web App config وتجربة متصفح.
- اختبار اختراق خارجي/مراجعة أمنية مستقلة لم تُجرَ.
